*ARRgh v1.5.0: DB backup & in-app restore

Released: 2026-09-28

Version level: MINOR. A new user-facing capability ships: admin-triggered and scheduled DB backups, restorable in-app. Also carries GH #249’s already-merged Home-page bug fix. No breaking API or config changes, and no new migrations.

Highlights

  • DB backup & in-app restore (GH #251). Settings → Backups lets an admin snapshot the whole application database — titles, chapters, progress, settings, users — to a destination they choose (point it at a NAS for off-box durability), on demand or on a schedule. Restore picks a listed backup or an uploaded .db file; a backup newer than the running app’s schema is refused, and a failed or rejected restore never touches the live database.
  • Home page shows its greeting on an empty library (GH #249). The greeting header only rendered once a title existed; a fresh install or wiped library showed no header until the first item was added.

What’s new

DB backup & restore (GH #251)

  • Backup now (POST /api/backups) — an atomic, consistent snapshot via SQLite’s own VACUUM INTO, safe to run while the library is syncing or downloading. Each backup is its own timestamped file (arrgh-backup-{YYYY-MM-DDTHH-MM-SS}.db), never overwriting a previous one; two backups landing in the same second still produce two distinct files.
  • Scheduled backups — an admin-configurable interval (Settings → Backups, default 24h, mirrors the existing library re-sync interval setting) triggers the same backup automatically. No destination configured → the schedule is a silent no-op, not an error.
  • List & delete (GET/DELETE /api/backups/{filename}) — filename, size, and creation time for every backup at the configured destination.
  • Restore (POST /api/backups/{filename}/restore, POST /api/backups/restore-upload) — pick a listed backup or upload a .db file from your own device. The candidate is validated before anything live is touched: it must be a genuine SQLite file, and its schema version must be no newer than the running binary’s own migrations. On success the app swaps the file in and restarts (docker-compose.yml’s restart: unless-stopped brings it back up); a restored file that predates the running app’s migrations is brought up to date automatically on that restart, the same guarantee every normal boot already provides.
  • Every backup/restore route is admin-only.

This is the belt-and-suspenders layer on top of already being able to point DatabasePath itself at durable storage (e.g. the same NAS volume as DownloadDir) — no code change needed for that; this feature adds point-in-time recovery and migrate-to-a-new-host on top.

Home page empty-library fix (GH #249)

GreetingJumbotron was nested inside the “library has items” branch, so a fresh or wiped install showed no header at all until the first title was added. It now renders unconditionally.

Upgrading

docker compose pull
docker compose up -d
  • No migrations, no new env vars.
  • Backups are opt-in — nothing happens until an admin sets a destination in Settings → Backups. Existing installs are unaffected until then.
